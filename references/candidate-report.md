# 用户能裁定的候选汇报

## 写法约束

用户解释区只使用需求与目标项目的语言。禁止堆放候选项目内部角色、模块缩写、状态名称或服务术语；即使附解释也不要用它们组织主体叙述。把“某内部发送协调器”写成“在发送前检查会话是否仍有效的逻辑”。

项目名、公开产品名和用户已使用的目标术语可以保留。精确文件/符号放在单独证据区，不能让用户靠阅读证据才理解结论。

事实与推断就地标明。表格用于概览，不能以表格代替每个候选的完整说明。

## 1. 开头先对齐目标

用两三句话说明这轮找什么、目标接入位置和待确认需求。说明这轮是静态研究还是包含已授权验证；不要把旧的其他环境证据当作本轮测试。

## 2. 概览表（可裁剪列，不固定数量）

| 候选/路线 | 现成满足的能力 | 主要缺口 | 需要带入/改动 | 关键风险/未知 | 推荐条件 |
|---|---|---|---|---|---|

候选过多时，只把具有真实选择价值的方案展开，其余列入淘汰记录并给理由。不得只展开推荐项、把入选备选敷衍成一句。

## 3. 每个入选候选的说明卡

```text
它为我们做什么：用目标语言解释核心作用。
怎么接入：现有谁调用它；采用库、包装、抽取、扩展还是组合。
对需求的覆盖：按需求编号说明现成/适配/自建/缺失/未知。
能保留什么：核心实现与现成行为。
要自己做什么：适配、替换依赖、缺失能力与目标项目改动。
运行条件：必须的包、服务、平台、状态和生命周期。
优势与代价：接入复杂度、运行负担、风险和长期维护。
许可与上游情况：观察事实及未核实内容。
证据强度：看到了什么、实际跑了什么、还不能证明什么。
验证重点：决定这条路线是否成立的关键假设。
```

每项围绕选择展开，不要求固定字数。无关的原项目功能不介绍；不要全量列原项目架构。

## 4. 推荐与用户交接

说明推荐依赖哪些假设。如果用户更重视少依赖、完整功能、少修改或上游升级，排序可能如何变化。用户决定取舍，不把评分或“最佳实践”当裁定。

提供自然的下一步：选候选、选组合、改需求、补证据、扩大搜索、放弃复用。最多两个问题，避免重复问已确定项。

选定之后先写验证计划并询问授权；不自动安装、执行、修改或接入。

## 5. 独立证据区

为每个候选提供：上游URL与固定版本、文件/符号、对应结论、证据类型、局限。可链接源码但不搬大段代码或整篇文档。

示例：

```text
E1：仓库/提交/文件/符号 → R2错误行为（源码观察，未运行）
E2：同版本测试及夹具 → 原项目只覆盖单实例（阅读测试，未运行）
E3：测试命令/环境/结果 → 受控失败清理（实际运行，未真实服务联调）
```

用户讲解与证据分开不是隐藏风险：影响选择的事实必须在主体里用可理解语言说明。
