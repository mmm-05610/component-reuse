# 来源、许可与长期可维护性

## 何时读取

候选涉及复制/改写源码、嵌入资源、新增依赖，或进入最终交付时读取。来源记录的形式可选，必要许可与版权义务不可因用户没选文档位置而省略。

## 1. 在建议采用前核查

检查对应版本的仓库许可、文件头、子目录独立许可、第三方嵌入代码、资源、NOTICE及生成文件来源。不能只看到根目录MIT就推断所有文件均相同。

无明确许可、混合条款或与项目发行方式可能冲突，列为待核实；没有证据不能宣布法律上可用。Agent不是法律审核者，复杂问题需合适的人工判断。

REUSE/SPDX可帮助表达和保留来源，工具通过不等于授权适用、许可兼容或安全性证明。不要为了使用一小块源码把整个项目强制改成REUSE格式。

## 2. 先问记录放在哪里

先找目标项目已有的第三方声明、依赖清单、vendor元数据、设计决策或来源记录。不重复建体系。

有合适位置则按惯例记录；不明确时询问。没有时提出默认方案，例如“放在采用组件附近的来源记录，许可声明沿用项目第三方声明位置”。没有批准位置前可在对话交付元数据，不擅自新增全仓规范。

## 3. 最小来源记录

按采用方式裁剪：

```text
用途与目标组件：
上游仓库/包：
版本/提交与取得日期：
采用方式：直接依赖 / 包装 / 抽取 / 分叉 / 组合 / 仅借鉴
采用文件/符号或锁定依赖：
对应许可、版权与必要声明位置：
上游原有部分：
本地适配、上游补丁、自建部分：
保留/新增测试与验证记录：
已知限制与未验证范围：
更新方式、负责边界和替换/退出办法：
```

直接依赖不需要虚构文件抽取清单；锁文件和已有第三方记录可承担部分内容。单一纯工具不必升级为完整SBOM或治理平台。

## 4. 更新不是“以后再复制一遍”

原样文件尽量保持可对照；修改需要能解释其原因和回归测试。不要去掉来源头、伪装为原创或把下游改动写成上游承诺。

说明升级的具体动作：更新版本/文件、重应用哪些补丁、跑哪些接口与行为测试。无法跟进上游时说明维护责任和替换成本，不承诺自动同步。

## 5. 最终检查

- 来源版本与实际采用版本一致。
- 声明覆盖实际复制文件、依赖及资源，不只写一个仓库链接。
- 原作者信息和必要声明仍保留。
- 能区分本地修改与上游能力。
- 用户能知道以后由谁维护、如何升级与如何退出。

参考：[FSFE REUSE Specification 3.3](https://reuse.software/spec-3.3/)。执行时若需使用具体工具或声明合规，重新核查其当前版本和适用条件。
