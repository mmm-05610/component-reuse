# 需求与目标接缝

## 1. 先读取目标项目

在许可范围内检查相关入口、公共接口、调用者、现有实现、构建和测试规则。不要全仓通读，更不要因为研究而切分支、改宿主或重构周边。

回答四件事：

1. 缺少的行为是什么；是否已有部分能力可用？
2. 预期使用者在何处调用；哪些接口和数据由目标项目拥有？
3. 当前项目对插件、依赖、进程、UI、存储有什么明确边界？
4. 现有测试/真实场景能否表达目标行为？

目标位置不明确时，把合理的接入位置建议交用户，而不是直接寻找改变整个架构的候选。

## 2. 澄清外部，不盘问内部

每轮最多两个问题，优先问会改变候选范围的事项。用户已表达清楚的内容不要反复确认。提供具体情境和可理解的选项，而不是问数据库、依赖注入框架或算法选型。

可覆盖：

| 维度 | 要弄清什么 |
|---|---|
| 用途 | 谁在什么情况下使用，成功给用户带来什么 |
| 输入/输出 | 输入来源、输出内容、可见操作和可接受的接口形式 |
| 失败 | 部分成功、错误反馈、不可用时行为 |
| 状态 | 保存什么、谁拥有、跨关闭/重启是否保留 |
| 生命周期 | 谁创建、何时结束、是否需要取消和恢复 |
| 约束 | 平台、离线、隐私、延迟、资源、许可和部署限制 |
| 排除 | 明确不做的功能，不能悄悄引入的能力 |

只选相关维度。纯格式化函数不需要完整恢复协议；持有进程的服务则不能忽略关闭语义。

## 3. 写成外部契约卡

这是工作记录模板，不是必须另建文件：

```text
要解决的问题：
目标项目中的使用位置/消费者：
必须满足：R1 …；R2 …
可取舍：R3 …
重要约束：
明确不做：
具体成功/失败示例：
已确定的接口（若有）：
待确认项：U1 …（可能影响哪些候选）
```

外部接口此时可以是“接受文本、返回可定位的片段并报告未找到”，不必提前固定语言级签名。已存在的签名、协议和错误格式则必须尊重。

把“快、可靠、可扩展”改写成场景：什么情况发生，期望如何反应，怎样判断满足。阈值由需求决定；不得编造毫秒数、成本或恢复保证。

## 4. 什么时候可以开始搜索

已明确用途、关键行为、目标接缝和影响路线的约束，即可研究。不要把“八成需求”变成问卷评分。

- 剩余问题可由候选差异帮助用户理解：标为待确认，继续。
- 剩余问题决定本地/云端、是否允许持久化等根本路线：先问。
- 用户指定内部实现：作为显式约束记录；不要擅自否定，发现代价时再展示取舍。
- 用户不知道内部怎么做：不要继续追问内部，把方案研究承担下来。

候选呈现是第二轮澄清。若用户改变需求，更新卡片并标记哪些既有结论需要重查，不丢掉有效证据。
